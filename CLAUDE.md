# Dashboard — instructions pour Claude Code

Backoffice **réservé au staff**. Aucune page publique hormis `/login`. Aucun SEO.
Déployé sur **Laravel Cloud**.

## Stack

| Couche        | Choix                                                                                                       |
| ------------- | ----------------------------------------------------------------------------------------------------------- |
| Backend       | Laravel 13, PHP 8.4, Fortify (auth), Reverb (websockets)                                                    |
| Frontend      | Inertia v3 + React 19 + TypeScript strict, Vite (vite-plus), Tailwind v4                                    |
| UI            | shadcn/ui (`resources/js/components/ui`, plus la Dropzone Kibo UI via le registre `@kibo-ui`), Lucide icons |
| Routes typées | Wayfinder (`resources/js/routes`, `resources/js/actions`, générés, non versionnés)                          |
| Temps réel    | Laravel Echo (`@laravel/echo-react`) + Reverb                                                               |
| Tests         | Pest (PHP), Vitest + Testing Library (front)                                                                |
| Qualité       | Pint, PHPStan/Larastan niveau 7, oxlint + oxfmt (`vp check`), `tsc --noEmit`                                |
| DB            | SQLite en local, Postgres/MySQL sur Laravel Cloud                                                           |

## Commandes (Makefile)

```
make install   # composer + npm + .env + clé + migrations
make start     # serveur HTTP + queue + Reverb + Vite + logs  (= composer dev)
make clean     # optimize:clear + purge du build Vite
make fresh     # migrate:fresh --seed (fixtures : admin@admin.fr et admin2@admin.fr, mdp "admin")
make test      # Pest puis Vitest
make lint      # Rector + Pint + oxlint/oxfmt --fix
make refactor  # Rector en dry-run
make hooks     # active le hook git pre-commit (fait par make install)
make types     # PHPStan + tsc
make check     # lint + types + test — à lancer avant chaque commit
make build     # build de prod des assets
make e2e       # tests navigateur Playwright (serveur `make start` + base seedée requis)
make e2e-ui    # idem en mode interactif (--ui)
```

Un hook **pre-commit** (`scripts/hooks/pre-commit`, activé via `core.hooksPath`) lance `make check` : un commit rouge est refusé. Ne jamais contourner avec `--no-verify`.

Comptes staff : **pas d'inscription**. Créer un membre avec :

```
php artisan staff:create --name="Nom" --email=nom@exemple.com --role=admin|manager|member
```

ou depuis le backoffice, **Paramètres › Équipe** (`settings/team`, route `team.index`, `App\Http\Controllers\Settings\TeamController`, middleware `role:admin`, entrée du menu des paramètres visible seulement avec `auth.can.manageStaff`) : liste des membres ayant accès au dashboard (nom, e-mail, rôle, 2FA, date d'arrivée, « (vous) » sur son propre compte), dialogue « Ajouter un membre » (`TeamMemberDialog` : nom capitalisé, e-mail, rôle, mot de passe confirmé ; `StoreStaffMemberRequest` = règles de `CreateStaffMember::rules()` + `confirmed`, route `team.store`) et « Retirer l'accès » avec confirmation (`team.destroy`, `DeleteStaffMember` ; `UserPolicy::delete` interdit de se retirer soi-même, le bouton est masqué via `can_delete`). `CreateStaffMember` et `DeleteStaffMember` diffusent `DashboardUpdated` ressource `staff`. Les membres sont routés par **UUID** (`users.uuid`, `User::getRouteKeyName()`), l'entier répond 404. Types `TeamMember`, `StaffRoleOption`, `TeamMemberForm` dans `resources/js/types/auth.ts`, fixtures `makeTeamMember()` et `staffRoles` dans `resources/js/test/fixtures/user.ts`.

## Langue : tout en français

- `APP_LOCALE=fr`, `APP_FALLBACK_LOCALE=fr`. Les traductions Laravel (validation, auth, passwords, Fortify) viennent de `laravel-lang/common` (`php artisan lang:update` après une montée de version). Les chaînes applicatives passent par `__('...')` avec leur traduction dans `lang/fr.json`.
- Tout texte affiché dans le front (libellés, placeholders, titres `<Head>`, `aria-label`, toasts, messages d'erreur) est écrit directement en français, vouvoiement. Le nom du produit reste « Dashboard ».
- Les tests assertent les textes français.
- **Noms de personnes toujours capitalisés** : tout prénom ou nom enregistré passe par `App\Support\PersonName::capitalize()` (initiale de chaque mot en majuscule, aussi après tiret ou apostrophe, reste en minuscules, espaces réduits) : `LeadData`, `DocumentRequestData` (personnes du foyer), `StaffMemberData`, `ProfileUpdateRequest` (`prepareForValidation`). Miroir front `capitalizeName()` dans `resources/js/lib/format.ts` pour les aperçus en direct. Le nom de client d'une facture (`client_name`, souvent une société) n'est **pas** normalisé.
- **Mot interdit : « staff »** dans tout texte visible (interface, e-mails, PDF, toasts, placeholders). Dire « l'équipe », « les membres », « le conseiller ». Le terme reste autorisé dans le code (identifiants, classes, canal `staff`, `StaffRole`, commentaires).

## Règles d'accès et SEO

- Toute route applicative est derrière le middleware `auth`. `/` redirige vers `login` ou `dashboard`. Seules exceptions : les webhooks signés `POST /webhooks/rip/contact` et `POST /webhooks/allo` (voir « Leads ») et la **page publique de dépôt des pièces** `GET|POST /depot/{jeton}` (voir « Liste de documents »), retrouvée par un jeton aléatoire de 48 caractères, jamais par un identifiant.
- Registration, reset password et vérification email sont **désactivés** dans `config/fortify.php`. Ne pas les réactiver.
- **« Se connecter avec Google »** (Laravel Socialite) : routes `auth.google.redirect` et `auth.google.callback` (`GoogleLoginController`, groupe `guest`, `throttle:10,1`, **404 sans `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`**). Le compte Google **ne crée jamais de membre** : `App\Actions\Auth\SignInWithGoogle` retrouve un membre existant par son e-mail (insensible à la casse), refuse sinon avec un message sur la page de connexion, et respecte `GOOGLE_ALLOWED_DOMAINS` (liste séparée par des virgules, vide = tous). Un membre avec la 2FA confirmée repasse par le défi Fortify (`login.id` en session, redirection vers `two-factor.login`) : Google ne contourne pas le second facteur. Le front reçoit `features.googleLogin` et `LoginForm` n'affiche le séparateur « Ou » et le bouton (`GoogleLoginButton`, lien plein navigateur vers la redirection OAuth) que dans ce cas.
- 2FA, passkeys et confirmation de mot de passe restent actifs (côté authentifié uniquement). **La page de connexion ne propose pas les clés d'accès** : `LoginForm` n'affiche que e-mail, mot de passe, « Se souvenir » et, si Google est configuré, le bouton Google (jamais de bouton « Se connecter avec une clé d'accès ») ; `PasskeyVerify` reste utilisé par la confirmation de mot de passe et les clés se gèrent dans Paramètres › Sécurité.
- `App\Http\Middleware\NoIndex` est **global** (`$middleware->append`, pas seulement le groupe `web`) : `X-Robots-Tag: noindex, nofollow, noarchive` sur toutes les réponses, y compris `/up`, `/pulse`, `/storage` et les assets des paquets ; `public/robots.txt` bloque tout, le layout Blade porte `<meta name="robots" content="noindex">`. Ne jamais ajouter de sitemap, d'OpenGraph ni de meta SEO.

## Rôles et autorisations

- Enum `App\Enums\StaffRole` : `admin` > `manager` > `member` (colonne `users.role`, castée). Pour ajouter un rôle : un cas + son label + son rang dans l'enum, puis les règles dans les Policies. **Droits par section** : `App\Enums\SiteSection` × `App\Enums\AccessLevel` (`none`, `read`, `write`, `manage`), niveau par défaut selon le rôle (`SiteSection::defaultLevel()` : admin = manage partout, manager = write, member = write sauf devis et factures en lecture), surcharges par membre dans `users.permissions` (page Équipe, `UpdateStaffAccess`), `User::canRead/canWrite/canManage`, middleware global `EnsureSectionAccess` (route → sections via `SiteSection::forRoute()`, y compris `owners.leads.*`) et Policies qui lisent ces niveaux. `LeadPolicy` dérive la section d'un lead (`LeadPolicy::section()` : converti → Clients, gestion locative → Leads propriétaires, sinon Leads) : un accès « Clients » seul ne modifie jamais un lead en cours. **Dernier administrateur** : `DeleteStaffMember::isLastAdmin()` interdit de le supprimer (page Équipe ou son propre profil, qui passe par la même action) et `UpdateStaffAccess` de le rétrograder. **Adresse e-mail d'un membre** : seul un admin la change (`ProfileUpdateRequest`), car elle sert d'expéditeur des e-mails aux leads quand son domaine est vérifié.
- Helpers modèle : `$user->isAdmin()`, `$user->hasRole(...$roles)`, `$user->hasRoleAtLeast($role)`.
- **Policies** dans `app/Policies` (une par modèle, `final`, suffixe `Policy`). `UserPolicy` : seuls les admins gèrent le staff, chacun voit et modifie son propre profil, un admin ne peut ni se supprimer ni changer son propre rôle.
- **Middleware de route** `role:admin,manager` (`App\Http\Middleware\EnsureStaffRole`) pour restreindre une route entière. Pour une action précise, utiliser la Policy (`$this->authorize()` ou `Gate`).
- Gates transverses dans `AppServiceProvider::configureGates()` (ex. `viewPulse`).
- **Téléphone du membre** : `users.phone` (string 40, nullable, format international « +33 6 12 34 56 78 » tel que saisi par `PhoneInput`), champ « Téléphone (pour les alertes par SMS) » sur la page Profil (`PhoneInput` avec `name="phone_national"` et un champ caché `phone` portant le numéro complet ; `ProfileUpdateRequest` : facultatif, blanc → null, refusé si `PhoneNumber::e164()` ne sait pas le normaliser), exposé dans `auth.user.phone`. Il sert aux SMS d'alerte de premier contact (voir Leads).
- **Photo de profil** : supprimée du disque avec le compte (`DeleteStaffMember`), comme les photos d'un bien supprimé (`DeleteProperty`). `users.avatar_path` sur le disque `public` (dossier `avatars/`, nom de fichier aléatoire généré par `store()` : l'URL n'est pas devinable, ce qui suffit pour des portraits de l'équipe ; décision prise de ne pas passer par une route authentifiée pour ne pas dépendre d'un disque privé sur Cloud), accessor `User::avatar` (URL ou `null`, ajouté au JSON). Routes `profile.avatar.update` (POST, `AvatarUpdateRequest` : JPG/PNG/WebP, 2 Mo) et `profile.avatar.destroy`, actions `App\Actions\Settings\{UpdateProfileAvatar,RemoveProfileAvatar}`. Front : `AvatarUpload` (`resources/js/components/settings`) sur la page Profil, envoi immédiat en multipart. `php artisan storage:link` est lancé par `make install` ; sur Laravel Cloud, prévoir le lien dans la commande de déploiement ou un bucket pour le disque `public`.
- **Droits par section** : chaque membre a un **niveau d'accès** (`App\Enums\AccessLevel` : `none` Aucun accès, `read` Consulter, `write` Modifier, `manage` Gérer ; `rank()`, `atLeast()`, `options()` avec description) sur chaque **section du site** (`App\Enums\SiteSection` : `leads`, `leads_create`, `owner_leads`, `owner_leads_create`, `clients`, `visits`, `agents` (agents **et** agences, indissociables), `partners`, `owners`, `properties`, `quotes`, `invoices`, `documents`, `reports`, `activity` (le journal se ferme sans fermer les rapports) ; `label()`, `group()` = groupe du menu, `manageHint()` = ce que « Gérer » ajoute, `hasManage()` = faux là où « Gérer » n'ajoute rien (`leads_create`, `owner_leads_create`, `clients`, `reports`, `activity`) et `clamp()` qui y ramène « Gérer » à « Modifier » — la matrice des droits ne propose alors que trois niveaux (`levelsFor()`), `forRoute($name)` = sections qui ouvrent une route d'après son nom, vide = route libre comme le tableau de bord et les paramètres ; `leads.index` n'appartient qu'aux leads locataires, une fiche lead s'ouvre avec l'une des deux listes, `tools.index` avec n'importe quel outil). **Défauts par rôle** (`SiteSection::defaultLevel($role)`, `roleDefaults()`) : admin = Gérer partout, manager = Modifier partout, membre = Modifier partout sauf devis et factures en Consulter (ce sont les règles historiques). **Personnalisation** : `users.permissions` (JSON section → niveau, seules les différences avec le rôle sont stockées, null = droits du rôle ; ignoré pour un admin qui gère toujours tout), `User::accessLevel($section)`, `canRead/canWrite/canManage(...$sections)` (vrai si une des sections atteint le niveau), `hasLevel()`, `hasCustomPermissions()`, `accessLevels()` (carte complète pour le front). **Toutes les Policies métier passent par ces niveaux** : `viewAny`/`view` = Consulter, `create`/`update` = Modifier, `delete` = Gérer (`CatalogDocumentPolicy` = Gérer les documents ; `LeadPolicy` consulte et modifie via leads, leads propriétaires ou dossiers clients, crée via l'une des Converting Machines). Middleware **`EnsureSectionAccess`** dans le groupe `web` : 403 si aucune section de la route n'est au moins consultable. **Une route sans section passe pour tout le monde** : `tests/Feature/Audit/RouteSectionCoverageTest.php` échoue donc si une route nommée n'est ni rattachée à une section, ni inscrite dans sa liste `FREE_ROUTES` avec sa raison — une route ajoutée et oubliée ne peut plus rester ouverte sans qu'on le voie. **Fonctions** : `users.functions` (JSON) parmi `App\Enums\StaffFunction` (`dossiers` Gestion des dossiers, `visits` Agent de visite, `closing` Closing et devis, `prospecting` Prospection propriétaires, `billing` Facturation, `partners` Relations partenaires ; `User::staffFunctions()`), affichées en badges sur la page Équipe et en libellés (`staff[].functions`) là où l'on choisit un membre (assignation d'une visite, menu « Suivi par » des leads).

Enregistrement par `team.access` (PATCH `settings/team/{member}/access`, `UpdateStaffAccessRequest` : `role` facultatif, `permissions` facultatif = niveau par section, `functions[]`), Action `App\Actions\Staff\UpdateStaffAccess` (`DashboardUpdated` ressource `staff`), `UserPolicy::updateAccess`. Helpers purs `resources/js/lib/team-access.ts` (`groupSections`, `customizedSections`, `setEveryLevel`, `defaultsFor`, `summarize`). Côté front, `auth.access` (carte section → niveau) est partagée et `filterNavGroups()` (`resources/js/lib/nav-access.ts`) retire de la sidebar les sous-liens au niveau `none` (`NavSubItem.section`), les menus vidés et les groupes vides ; un menu dépliable garde sa propre page (« Outils » → `tools/index`) et ne bascule sur son premier sous-lien restant que si sa cible a été fermée, les menus vidés et les groupes vides. Tests : `tests/Feature/Staff/StaffAccessTest.php`, `__tests__/lib/nav-access.test.ts`, `__tests__/pages/settings/{team,team-member}.test.tsx`, fixtures `memberAccess`, `roleDefaults`, `accessLevels`, `siteSections`, `staffFunctions`, `makeTeamMemberAccess()`.

## Temps réel (obligatoire pour toute action du backoffice)

Quand un membre du staff fait une action, les autres membres connectés doivent la voir **sans refresh**.

1. Côté PHP, après la mutation, dispatcher `App\Events\DashboardUpdated::dispatch('<resource>', [...payload], 'a expédié la commande #42')`.
   L'événement embarque l'acteur (utilisateur connecté) et le message, et part sur le canal de présence `staff` (autorisation dans `routes/channels.php`), nom `dashboard.updated`. Le message est une phrase à la 3e personne sans sujet : le front la préfixe du nom de l'acteur.
2. Côté React, `<RealtimeStaff />` est monté une fois dans le header du layout authentifié : pour chaque événement reçu, il affiche un toast « Admin 2 a expédié la commande #42 » (ou « Vous (autre onglet) : … ») puis recharge les props Inertia de la page courante. L'onglet auteur de l'action est exclu **par socket** : `attachSocketIdToInertia()` (`resources/js/lib/socket-id.ts`, appelé dans `app.tsx`) ajoute l'en-tête `X-Socket-ID` à chaque visite Inertia et `DashboardUpdated` appelle `dontBroadcastToCurrentUser()`. Les autres onglets et navigateurs du même utilisateur reçoivent bien l'événement.
   Une page qui veut un rechargement ciblé ou une mise à jour optimiste appelle `useStaffChannel({ only: ['orders'], notify: false, onEvent })` (`resources/js/hooks/use-staff-channel.ts`).
   Les liens de navigation utilisent `prefetch` (cache Inertia de 30 s) : `flushPrefetchOnMutations()` (`resources/js/lib/prefetch-cache.ts`, appelé dans `app.tsx`) vide ce cache avant toute visite non-GET, et `useStaffChannel` le vide à chaque événement reçu, pour qu'une liste préchargée ne soit jamais périmée après une création ou une modification.
3. `<OnlineStaff />` (header) affiche les avatars des membres connectés via `useOnlineStaff()` (canal de présence).
4. Créer un événement dédié seulement si le payload devient métier (ex. `OrderShipped`). Il doit alors implémenter `ShouldBroadcastNow` (ou `ShouldBroadcast` via la queue) et diffuser sur `PresenceChannel('staff')`.
5. `DashboardUpdated` implémente `ShouldDispatchAfterCommit` : levé dans une transaction, il ne part qu'au commit (jamais de toast fantôme sur un rollback, ni de rechargement avant l'écriture). Un événement dont le payload `mentions` vise d'autres membres (rappels, alertes) est ignoré par `useStaffChannel` chez tout le monde sauf les membres cités (`targetsOthers()`). `DashboardUpdated` est diffusé **immédiatement** (`ShouldBroadcastNow`, pas de queue) pour que les autres membres voient l'action sans délai. La connexion `reverb` de `config/broadcasting.php` enveloppe `reverb-raw` dans `App\Broadcasting\ResilientBroadcaster` (driver `resilient`, enregistré dans `AppServiceProvider::configureBroadcasting()`) : si Reverb est injoignable ou mal configuré, l'erreur est signalée dans les logs et la requête aboutit quand même, jamais de 500 à cause du temps réel. Un événement métier dédié peut rester en queue (`ShouldBroadcast`) s'il fait un travail lourd. **Tous les mailables de `app/Mail` implémentent `ShouldQueue`** : `Mail::to()->send()` les met en file, la latence SMTP sort de la requête et un envoi raté est rejoué. Les tests assertent donc `Mail::assertQueued()` / `assertNotQueued()` / `assertQueuedCount()`, jamais `assertSent()`. Le rendu DocRaptor et l'appel Yousign restent **dans la requête** : leur résultat (lien de contrat, erreurs de validation) est montré au conseiller sur-le-champ. En local, `.env` doit avoir `BROADCAST_CONNECTION=reverb` (avec `log`, rien n'est diffusé) et tout changement de `.env` lié à la diffusion demande de relancer `make start`.

Echo est configuré dans `resources/js/app.tsx` via `configureEcho({ broadcaster: 'reverb' })` et lit les variables `VITE_REVERB_*`.

## Factures (relocation à Paris)

- Société suisse : devises `CHF` ou `EUR` (`App\Enums\Currency`), TVA par défaut 8,1 %, coordonnées et prix par défaut dans `config/company.php` (surchargés par les variables `COMPANY_*` et `OFFER_*` de `.env`).
- Deux offres seulement : `App\Enums\Offer` (`accompagne`, `confie`). Une ligne de facture = offre + quantité + prix unitaire en centimes, la description est générée par l'enum.
- Création : `StoreInvoiceRequest` → `InvoiceData` / `InvoiceLineData` (totaux calculés dans le DTO) → `CreateInvoice` (numéro `RP-27NNN` séquentiel, transaction, première entrée d'historique, `DashboardUpdated`). Une facture naît **toujours en brouillon** (le formulaire n'accepte pas de `status`). Bornes serveur : 50 lignes, quantité ≤ 10 000, prix et acompte ≤ 1 000 000 en unités, acompte ≤ total (`after()`). `nextNumber()` (factures et devis) trie par longueur puis valeur (`RP-271000` passe après `RP-27999`) et verrouille la dernière ligne (`lockForUpdate`).
- Page `invoices/create` : en-tête en `justify-between` avec, à droite, le menu « ⋯ » `CreateFromMenu` (`resources/js/components/invoices/create-from-menu.tsx`) — « Depuis un devis » (recherche `tools.quotes.search` puis `tools.quotes.invoice` qui convertit le devis en facture) et « Depuis un client » (recherche `leads.search` puis retour sur la page avec `?lead=UUID` pour préremplir) ; le même menu, sans l'entrée devis, coiffe `quotes/create`. Formulaire `useForm` Inertia avec aperçu en direct (`InvoicePreview`), calcul des totaux partagé dans `resources/js/lib/invoice-totals.ts` avec les mêmes arrondis que le PHP. Le formulaire saisit des unités, le `transform` envoie des centimes.
- Liste `invoices/index` : Data Table shadcn (TanStack v8) en **mode serveur** : `IndexInvoicesRequest` (`q` numéro ou client, `status`, `sort` parmi `IndexInvoicesRequest::SORTS`, `dir`, `page`), `paginate(50)->withQueryString()`, props `invoices`, `pagination` `{current_page, last_page, per_page, total}`, `filters` `{q, status, sort, dir}`, `overdueCount` (retards sur l'ensemble). Côté front, `useServerTable()` (`resources/js/hooks/use-server-table.ts` : recherche 300 ms après la frappe, page, tri → `router.get` avec `only`, `preserveState`, `replace`) alimente la prop `server` de `DataTable` (`manualPagination` / `manualFiltering` / `manualSorting`, « Page n sur m », total serveur dans le pied) ; réutilisable pour toute autre liste volumineuse. Pagination masquée en dessous d'une page. Chaque ligne de la `DataTable` est identifiée par l'`uuid` (sinon l'`id`) de son enregistrement via `getRowId`, jamais par sa position : un tri ne déplace donc plus l'état porté par les cellules (étoile de favori, cases cochées). **Actions groupées** : la Data Table accepte `bulkActions(rows, clearSelection)` rendu dans un îlot flottant `sticky bottom-4` centré sur le tableau dès qu'une ligne est cochée (compteur, actions, bouton Désélectionner) ; le numéro de facture est un lien vers la fiche ; `InvoiceBulkActions` (managers et admins seulement) propose « Envoyer (n) » et « Marquer payées (n) » avec le nombre d'éligibles (`can_send` / `can_pay`), routes `invoices.bulk-send` / `invoices.bulk-pay` (`BulkSendInvoicesRequest`, `BulkPayInvoicesRequest`, déclarées avant `invoices/{invoice}`), Actions `SendInvoices` / `MarkInvoicesPaid` qui délèguent à l'unité et renvoient les numéros traités et ignorés, résumés dans un toast (succès, ou avertissement listant les ignorées).
- **Lien lead ↔ facture** : `invoices.lead_id` (nullable, `Invoice::lead()`, `Lead::invoices()`). Route `invoices.link` (PATCH, `LinkInvoiceLeadRequest`, `LinkInvoiceToLead`, `lead_id` null pour détacher, note ajoutée au lead) ; recherche JSON `invoices.search` (numéro, client). Côté front : `InvoiceLeadLink` sur la page facture (lead rattaché, recherche via `leads.search`, détacher), `LeadInvoices` dans la section « Factures » de la fiche lead (liste, « Créer une facture » qui ouvre `invoices.create?lead=ID` avec `prefill` client/devise/formule et `lead_id` envoyé au `store`, « Lier une facture existante »). Managers et admins seulement.
- Droits : `InvoicePolicy`, tout le staff consulte, managers et admins créent et modifient, admins suppriment.
- **PDF** : route `invoices.pdf`, vue Blade `resources/views/invoices/pdf.blade.php` rendue puis envoyée à DocRaptor (`App\Services\DocRaptor`, clé `DOC_RAPTOR_KEY`, `DOC_RAPTOR_TEST_MODE=true` ajoute un filigrane sans facturation). Les tests simulent l'API avec `Http::fake`.
- **Adresse** : autocomplétion Google Places via le proxy Laravel (`PlacesController`, routes `places.suggest` et `places.details`, `App\Services\GooglePlaces`, clé serveur `GOOGLE_MAPS_API_KEY`, jamais exposée ; la clé navigateur `GOOGLE_MAPS_BROWSER_KEY` sert uniquement à la carte des arrondissements). Le front (`AddressAutocomplete`) reçoit `features.addressAutocomplete` en prop partagée ; sans clé, le champ est un simple texte.

## Identifiants publics (UUID dans les routes)

- **Migrations et MySQL** : en local la base est SQLite, en production MySQL — leurs refus ne portent pas sur les mêmes choses, et une migration verte en local peut casser le déploiement. Deux règles tirées d'un échec réel (« Cannot drop index … needed in a foreign key constraint », erreur 1553) : **supprimer une clé étrangère avant l'index qui la porte** (MySQL s'appuie sur cet index ; SQLite, lui, refuse de supprimer une colonne encore indexée ou porteuse d'une clé — l'ordre clé → index → colonne satisfait les deux), et **rendre chaque migration rejouable** (`Schema::hasColumn`, `hasIndex`, existence de la clé étrangère), un déploiement interrompu reprenant la migration depuis le début.
- **Règle** : aucune route ne porte l'identifiant numérique d'un enregistrement. Tout modèle exposé dans une URL (`Lead`, `LeadNote`, `Invoice`, `Quote`, `DocumentRequest`, `CatalogDocument`, `Agency`, `Agent`) a une colonne `uuid` (unique, générée à la création par `HasUuids` avec `uniqueIds()` = `['uuid']`, la clé primaire reste l'entier `id`) et `getRouteKeyName()` renvoie `uuid` : un entier dans l'URL répond 404. Migrations `2026_09_07_16xxxx_add_uuid_to_<table>_table.php` sur le motif de celle des leads (colonne nullable, remplissage `Str::orderedUuid()`, puis non nulle et unique).
- **Sérialisation** : les contrôleurs exposent `uuid` à côté de `id` ; les types TS portent `uuid: string` et les routes Wayfinder prennent `{ invoice: invoice.uuid }` (les helpers générés acceptent `{ uuid }`). L'`id` numérique reste pour les comparaisons, les clés étrangères (`lead_id`, `agency_id`…) et les payloads (`invoice_ids`, `ids`, `mentions`). Les fixtures front (`resources/js/test/fixtures/*`) ont un `uuid` déterministe.
- **Nouveau modèle routé** : appliquer le même motif dès la migration de création, et ajouter un test « routes use the UUID and refuse the numeric id » (voir `tests/Feature/Invoices/InvoiceLifecycleTest.php`, `tests/Feature/Quotes/QuotePublicIdentifierTest.php`, `tests/Feature/RealEstate/RealEstatePublicIdentifierTest.php`, `tests/Feature/Leads/LeadNotePublicIdentifierTest.php`).

## Architecture et conventions

Ces règles sont **vérifiées par `tests/Architecture/ArchitectureTest.php`** (pest-plugin-arch). Une violation casse la suite.

- `declare(strict_types=1)` dans tout `app/`. Pas de `dd`, `dump`, `env()` hors `config/`.
- `config/pulse.php` et la migration Pulse sont publiés par le package : exclus de Rector et PHPStan, ne pas les retoucher.
- **Actions** (`app/Actions/<Domaine>/<Verbe><Nom>.php`) : classe `final`, une méthode `handle()`, injectable, sans dépendance HTTP. Toute logique métier vit là, jamais dans les contrôleurs ni dans les commandes. Exemple : `App\Actions\Staff\CreateStaffMember`.
- **DTOs** (`app/Data/<Nom>Data.php`) : `final readonly`, constructeur nommé, `from(array)` et `toArray()`. Une Action reçoit un DTO dès qu'elle a plus de deux paramètres. Exemple : `App\Data\StaffMemberData`.
- **Form Requests** (`app/Http/Requests`, suffixe `Request`) pour toute validation HTTP. Le contrôleur construit le DTO depuis `$request->validated()` et appelle l'Action.
- **Contrôleurs** fins : Form Request, Action, réponse Inertia ou redirection. Jamais de `DB::` ni de `Validator::` dedans.
- **Enums PHP** (`app/Enums`) pour tout état métier, castés dans le modèle. Jamais de chaînes magiques.
- **Policies** (`app/Policies`) dès le premier modèle métier, même si tout le staff a les mêmes droits aujourd'hui.
- **Commandes artisan** `final`, déléguant à une Action.
- **Événements** dans `app/Events`, **commandes** dans `app/Console/Commands`, **middlewares** dans `app/Http/Middleware`.
- Si un domaine grossit (plusieurs modèles, règles métier riches), passer à une organisation par domaine `app/Domain/<Contexte>/{Actions,Models,Events,DataTransferObjects}` (DDD léger). Ne pas le faire de manière préventive.
- Pas de logique dans les modèles hors relations, casts, scopes et accessors.
- Typage strict partout : types de retour PHP, `declare` de propriétés, TS `strict` sans `any`.
- Pages Inertia dans `resources/js/pages/<domaine>/<page>.tsx` (kebab-case). Layouts choisis dans `resources/js/app.tsx`.
- **Formulaires** : un seul style, celui de « Planifier une visite ». Chaque bloc passe par `FormSection` (`resources/js/components/form-section.tsx`) : carte `bg-background rounded-lg border p-4`, en-tête pictogramme dans une pastille `bg-primary/10` + titre `text-sm font-medium` + phrase d'aide `text-xs`, filet `border-b` sous l'en-tête, `action` pour un bouton à droite ; `FormGrid` pour la grille de champs (une colonne, deux à partir de `sm`), champ = `grid gap-2` (Label, champ, `InputError`), blocs espacés de `gap-4`. `variant="plain"` dans un dialogue, qui est déjà une carte. `FormGroup` (`lead-form-shell.tsx`) et les groupes encadrés de `PropertyFields` délèguent à `FormSection` : tout nouveau formulaire s'y conforme, page comme dialogue.
- **Modales** : `DialogContent` (`components/ui/dialog.tsx`) est retouché pour ne jamais déborder de l'écran — `max-h-[calc(100dvh-2rem)] overflow-y-auto overscroll-contain` : une modale trop haute défile en elle-même et la page derrière ne bouge pas. À reporter si le composant est régénéré (`npx shadcn add`), comme les retouches de `attachment.tsx` et `dropzone.tsx`. Test : `__tests__/components/ui/dialog.test.tsx`.
- **Tableaux** : tout doit être aligné. Largeurs posées sur les `TableHead` (avec `table-fixed` quand plusieurs tableaux se suivent sur une page, comme les journées de `VisitDaySection`), cellules en `align-top` dès qu'une colonne tient sur deux lignes, `tabular-nums` sur les heures, montants et références, `truncate` + `min-w-0` plutôt qu'une colonne qui s'élargit.
- **Toasts** : composant shadcn `Toast` (Base UI, `resources/js/components/ui/toast.tsx`, `<Toaster />` monté dans `app.tsx`). Ne jamais appeler le gestionnaire directement : passer par `notify` (`resources/js/lib/toast.ts`) : `notify.success/info/warning/error(titre, description?)`, et pour une opération longue `const id = notify.loading(...)` puis `notify.resolve(id, ...)` ou `notify.reject(id, ...)` qui font évoluer le même toast. Les tests mockent `@/lib/toast`. **Toute action importante confirme par un toast** : le toast est posé **côté serveur** (`Inertia::flash('toast', ['type' => 'success', 'message' => __('…')])` juste avant `back()` ou `to_route()`), pour que le message soit le même quel que soit l'écran qui déclenche l'action ; `notify.loading()` / `resolve()` côté React reste réservé aux opérations longues (PDF, visio, envoi au lead). Un double toast (serveur **et** `notify` dans le composant) est un défaut : garder celui du serveur. Seule exception assumée, les **favoris** restent silencieux (étoile personnelle, changement instantané et visible de son seul auteur).
- Composants shadcn dans `resources/js/components/ui` (ne pas éditer à la main, régénérer avec `npx shadcn add`). Composants applicatifs dans `resources/js/components`.
- Formulaires : composant `<Form>` d'Inertia + routes Wayfinder (`store.form()`), jamais d'URL en dur.
- Après ajout ou modification d'une route PHP : `php artisan wayfinder:generate --with-form` (fait automatiquement par Vite en dev).

## Ce qu'il ne faut pas faire

- Pas de page publique, pas de route sans `auth` (sauf celles de Fortify pour le login, 2FA, passkeys).
- Pas de réactivation de l'inscription ou du reset de mot de passe.
- Pas de logique métier dans les contrôleurs, commandes ou composants React.
- Pas de mutation côté backoffice sans `DashboardUpdated` (ou événement broadcast dédié).
- Pas de code sans test, pas de commit sans `make check` vert, pas de `--no-verify`.
- Pas de Repository au-dessus d'Eloquent, pas de couche Service en plus des Actions, pas de CQRS.

## Quand le projet grossit

- Passer à `app/Domain/<Contexte>/{Actions,Models,Events,Data,Policies}` dès que plus de deux modèles interagissent dans un même contexte.
- Remplacer `DashboardUpdated` par des événements métier nommés (`OrderShipped`) dès qu'un consommateur a besoin du payload.
- Générer les types TS depuis PHP (`spatie/laravel-typescript-transformer`) quand les props de page se multiplient.
- Observabilité : Laravel Pulse ou Nightwatch sur Laravel Cloud, `Log::withContext(['staff_id' => ...])` sur chaque requête.
